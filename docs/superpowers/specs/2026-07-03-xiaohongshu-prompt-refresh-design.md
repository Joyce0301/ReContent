# 小红书 Prompt 刷新设计

## 背景

当前 ReContent 的多平台改写链路中，小红书笔记使用的是一套较轻量的生成约束：

- 标题不超过 20 字
- 正文 300-800 字
- 适当分段、使用 emoji 和标签

这套规则可以快速生成可读结果，但在真实使用中暴露出两个问题：

1. 结果常常偏短，更像摘要，不像可直接发布或继续编辑的小红书笔记。
2. 内容虽然格式正确，但“小红书感”不够强，缺少场景切入、真人分享感和细节展开。

用户希望在不破坏现有 JSON 输出、个性化要求、失败重试和多平台链路的前提下，刷新小红书 prompt，让生成结果更贴近当前平台风格，并显著提升信息密度。

## 目标

本次只刷新小红书平台的生成规则，使输出同时具备：

- 小红书常见的真人分享感与场景感
- 比当前版本更详细的干货密度
- 与现有 prompt 架构兼容，不影响 Twitter / LinkedIn 规则

目标风格为：

- 外层像真实用户写的分享型笔记
- 内核是偏详细的干货经验型内容
- 最终效果介于“种草分享”和“知识拆解”之间，默认偏详细

## 非目标

本次不做以下改动：

- 不新增平台选择逻辑或单独的小红书模型路由
- 不新增“详细程度”配置项
- 不修改 Twitter / LinkedIn 的平台 prompt
- 不修改 API 请求结构和 JSON schema
- 不调整 URL 抽取器、fallback 策略或 provider 选择逻辑

## 外部风格依据

本次 prompt 刷新的风格依据来自 2025-2026 年可访问的公开资料，重点看“当前常见写法”和“平台/运营侧建议”：

- 小红书官方《商家热搜词发布攻略》强调：
  - 热搜词应自然出现在标题、正文、话题中
  - 正文要围绕核心词展开
  - 笔记要避免过强营销感
  - 排版要分段，不宜一整块大段文本
- 2025 年多篇运营复盘普遍强调：
  - 高表现内容更偏场景化、痛点化、真实故事化
  - 清单、干货、测评、教程、经验总结更容易获得收藏和搜索流量
  - 标题优先突出人群、痛点、场景和结果感
- 最近的实操总结中，知识/经验类笔记常见结构为：
  - 痛点场景 -> 方法拆解 -> 分点展开 -> 结果/总结 -> 互动收口

## 设计原则

### 1. 保留现有系统约束优先级

小红书风格刷新不能削弱以下硬约束：

- 只返回可解析 JSON
- 结果字段结构不变
- 不能虚构事实和数据来源
- 个性化要求只能补充风格，不能覆盖平台规则

### 2. 强化“小红书感”，但避免模板味

prompt 需要鼓励：

- 第一人称或贴近用户视角的表达
- 从具体场景、困惑、体验、观察切入
- 语言口语化、真诚、轻分享感

同时避免：

- 机械套模板
- 纯营销口吻
- 一上来就是新闻摘要或报告概述

### 3. 默认更详细，而不是更短更快

当前 300-800 字区间容易把模型引导成“总结型输出”。本次将明确把小红书正文目标调整为更详细的区间，并要求多段展开，优先解释：

- 为什么这个结论成立
- 具体有哪些要点
- 哪些人适用
- 真实使用/理解场景是什么

### 4. 保持内容可发，不做论文式长文

虽然要变详细，但仍然要保留小红书的阅读节奏：

- 短段落
- 清晰分层
- 有重点句
- 结尾有轻互动

目标是“详细但好读”，不是“信息很多但像报告”。

## Prompt 改动方案

仅修改 `app/api/repurpose/prompt-builder.ts` 中的平台规则生成方式和小红书平台描述，不改变 API 出参结构。

### 当前规则

- 小红书笔记：1 篇中文笔记，包含一个有吸引力的标题（不超过 20 字）和正文（300-800 字），正文适当分段、使用 emoji 和标签。

### 新规则方向

改为更明确的风格与结构约束，核心意图如下：

- 标题：
  - 仍然不超过 20 字
  - 优先体现人群 / 场景 / 痛点 / 收获感
  - 避免空泛标题、媒体标题、硬营销标题
- 正文长度：
  - 目标提升到约 700-1200 字
  - 明确要求不能只给几条简短 bullet 就结束
- 正文结构：
  - 开头先用一个具体场景、问题、感受或观察切入
  - 中间至少 3 个展开段，围绕核心观点进行细化说明
  - 每段尽量提供解释、例子、方法、对比或适用场景
  - 结尾给出一句轻互动或总结，不写生硬 CTA
- 文风：
  - 默认更像真人分享经验，而不是复述原文
  - 真诚、自然、弱营销感
  - 如用户个性化要求有明确风格倾向，可在不破坏平台结构的前提下微调口吻
  - 允许适量 emoji，但不堆砌
- 标签：
  - 3-5 个强相关标签
  - 不要用不相关热点凑数

### Conservative mode 补充

为了降低长文本导致的 JSON 解析风险，conservative mode 下的小红书规则会额外强调：

- 优先返回合法 JSON
- 如有必要，可适度降低细节密度
- 仍需保留核心信息与基本展开结构

## 推荐输出心智

如果原始内容是资讯、报告、英文文章或抽象观点，模型不应只做“翻译式缩写”，而应完成一次“小红书化改写”：

1. 先提炼出最适合小红书读者理解的切入点
2. 把抽象观点翻译成真实使用场景或具体问题
3. 用分享型表达包住干货内容
4. 保持事实边界，不添加原文没有依据的结论

## 对现有链路的影响

本次改动不会改变生成链路：

- 输入仍来自文本或 URL 抽取结果
- 后端仍根据 provider 调用 Kimi / OpenAI
- `buildRepurposeUserPrompt` 仍返回统一大 prompt
- 失败重试与 conservative mode 保持原逻辑

唯一变化是：

- prompt 只包含本次请求的平台规则与 JSON 示例
- 当请求包含小红书平台时，模型会收到更明确、更偏详细的风格约束

## 测试策略

本次至少补充或更新以下测试：

- `app/api/repurpose/prompt-builder.test.ts`

覆盖点包括：

- 小红书 prompt 包含新的正文长度目标
- 小红书 prompt 包含场景切入与分段展开要求
- 小红书 prompt 包含“真人分享感 / 弱营销感 / 详细展开”类约束
- 个性化要求存在时，仍然只作为补充风格要求
- conservative mode 下，新的风格描述不会破坏严格 JSON 约束

## 风险与权衡

### 风险 1：输出更长后，解析稳定性下降

这是本次最主要风险。更长的小红书内容可能增加模型偏离 JSON 或字段遗漏的概率。

缓解方式：

- 不修改 JSON 示例结构
- 保留 conservative mode 的强约束
- 只增强小红书风格说明，不引入复杂嵌套模板

### 风险 2：风格更像模板化内容

如果 prompt 写得过死，模型可能生成千篇一律的“痛点-方法-总结”套路文。

缓解方式：

- 描述结构偏好而不是硬模板
- 允许根据原文主题灵活组织中段内容

### 风险 3：与个性化要求冲突

用户可能输入“写得更冷静、更专业”之类要求，和小红书的分享感存在张力。

缓解方式：

- 继续保留“个性化要求只能补充风格，不覆盖平台规则”的层级
- 让个性化要求影响口吻，但不影响结构与平台适配

## 验收标准

- 代码层面：
  - `buildRepurposeUserPrompt` 中的小红书规则已更新为新的详细分享型约束
  - 测试覆盖新的小红书 prompt 要求并通过
- 行为层面：
  - 新 prompt 明确要求更长、更细、更像真人分享的小红书笔记
  - 不影响 Twitter / LinkedIn 的规则文本
  - 不改变 JSON schema、API 入参或 provider 调用方式
- 稳定性层面：
  - 现有 prompt-builder 测试通过
  - 相关 API 测试与构建不因本次 prompt 刷新而失败

## 后续演进

如果这次仅靠 prompt 刷新后仍觉得小红书内容偏短，下一步优先考虑：

1. 为平台生成切换成“一次只生成一个平台”
2. 对 URL 抽取结果增加“正文质量不足”识别与提示
3. 后续再评估是否需要单独加入“详细程度”控制项
